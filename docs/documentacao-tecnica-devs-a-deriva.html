1. Conclusão executiva

O projeto Devs à Deriva é um blog Astro com experiência visual forte em estética sci-fi/cyberpunk, conteúdo editorial dinâmico vindo de um dashboard externo e várias interações client-side. A camada pública do blog está separada do dashboard por uma fronteira HTTP definida por PUBLIC_DASHBOARD_URL.

Desde a análise original (05/05/2026) foram implementados: pipeline CI/CD completo com seis jobs (quality, build, audit, lighthouse, deploy, smoke), suite de testes unitários com Vitest, testes e2e com Playwright, scripts de validação de qualidade, healthcheck em /health.json, rollback automático pós-smoke, integração de Gitleaks e Dependency Review, paginação de categorias, página de newsletter, sitemap.xml dinâmico, llms.txt e AEO.

Em 13/05/2026 foram implementadas as configurações de segurança e proteção DDoS: proxy Cloudflare com WAF, SSL Full (strict), HSTS, Bot Fight Mode, rate limiting, firewall UFW na VPS e Fail2ban.

Em 05/2026 o blog migrou de SSG puro para modo híbrido SSR + estático com deploy duplo: Vercel (CDN/serverless) e VPS próprio (Docker + @astrojs/node standalone, nginx como proxy reverso). Novos posts aparecem em até 30 segundos sem rebuild, via cache TTL de 30s em fetchPosts(). Foram também adicionadas as páginas /busca e feed RSS (/rss.xml), o componente Newsletter.astro extraído para reutilização, melhorias no parser Markdown e padronização de cor de texto em posts.

O projeto está em estágio editorial funcional com infraestrutura de produção: CI robusto, deploy duplo com rollback, Lighthouse bloqueante, proteção DDoS e documentação completa.

3. Arquitetura do projeto

Modelo

Modo híbrido (estático + SSR seletivo): páginas com conteúdo dinâmico têm export const prerender = false e são renderizadas em runtime pelo servidor Node.js. Páginas de conteúdo fixo são pré-geradas como HTML estático. Isso elimina a necessidade de rebuild para publicar novos posts — um novo post aparece em até 30 segundos (TTL de cache em fetchPosts()).

Seleção de adaptador

astro.config.mjs detecta o ambiente via VERCEL=1 (setado automaticamente pela Vercel) e usa @astrojs/vercel no build da Vercel, ou @astrojs/node standalone em todo o resto (VPS, CI, local).

4. Fluxo de funcionamento

Build e runtime

  1. O build Astro inicia com npm run build. O adaptador é selecionado pela presença de VERCEL=1.
  2. Páginas estáticas são pré-geradas em tempo de build. Páginas SSR (prerender = false) são renderizadas em runtime.
  3. fetchPosts() em src/lib/posts.ts busca posts do dashboard e aplica cache em memória com TTL de 30 segundos em produção. Em desenvolvimento, o cache é desabilitado.
  4. O payload é normalizado: content (Markdown bruto) é convertido para HTML via parser próprio.
  5. A home (SSR) exibe os posts mais recentes em tempo real. Categorias, paginação e busca também são SSR.
  6. /health.json, /sitemap.xml, /ai-index.json e /rss.xml são endpoints SSR que refletem o estado atual do dashboard.
  7. O browser ativa animações canvas, comentários, newsletter e progresso de leitura via APIs do dashboard.

Fluxo CI/CD (resumo)

  1. Push na main ou PR dispara o pipeline.
  2. Job quality: lint, typecheck, validação de conteúdo, testes unitários, Gitleaks.
  3. Job build: astro build e upload do artefato dist/.
  4. Jobs audit e lighthouse (paralelos): SEO, links, segurança, Dependency Review, Lighthouse CI bloqueante.
  5. Job deploy: apenas em push na main, via SSH no VPS.
  6. Job smoke: wait até 75s, valida rotas públicas e /health.json. Se falhar, aciona rollback automático.

6. Pipeline CI/CD

Arquivo: .github/workflows/ci.yml (209 linhas). Pipeline completo com seis jobs sequenciais/paralelos.

Triggers

  • push na main: qualidade + build + auditoria + deploy + smoke.
  • pull_request para main: qualidade + build + auditoria + Lighthouse. Sem deploy.
  • repository_dispatch (tipo blog-rebuild): rebuild via webhook externo.
  • workflow_dispatch: trigger manual.

Rollback

scripts/deploy.sh salva o SHA anterior em /opt/devs-a-deriva/.previous-rev antes de cada deploy. Se o smoke falhar após um deploy bem-sucedido, o CI executa scripts/rollback.sh via SSH automaticamente. O script lê .previous-rev, faz checkout da versão anterior e reconstrói o Docker. Rollback de falha durante build também é coberto por trap ERR no próprio deploy.sh.

Componente parametrizado para páginas de categoria. Busca posts e destaques por categorySlug, renderiza header, contador, carrossel com dots/auto-play e grid de posts. Marca origem category em sessionStorage para a página de post ajustar labels e navegação.

Recebe postSlug, usa PUBLIC_DASHBOARD_URL, mostra textarea, prompt de login social, lista de comentários aprovados e estado vazio/loading. Monta comentários via DOM, usa textContent para o corpo e allowlist para providers OAuth. O envio cria draft no dashboard e redireciona para signInUrl.

StarBackground.astro

Três camadas CSS de estrelas com animações lentas. A cada intervalo cria um pequeno SVG de nave, anima opacidade e remove o elemento.

Newsletter.astro

649 linhas. Componente reutilizável de inscrição na newsletter. ErrorPage.astro

Componente visual para 404/500: separa dígitos do código, renderiza textos SVG com gradiente, helmet webp e CTA para home. Usado por 404.astro e 500.astro com hideNavbar.

14. SEO, acessibilidade e performance

SEO — implementado

Todos os itens marcados como "melhoria futura" na análise original foram implementados:

  • Canonical: tag <link rel="canonical"> gerada por rota em Base.astro.
  • Sitemap: /sitemap.xml gerado dinamicamente com todas as rotas públicas e posts.
  • robots.txt: presente em public/robots.txt.
  • OG tags: og:title, og:description, og:image em todas as páginas.
  • JSON-LD: structured data gerado em Base.astro.
  • AEO/GEO: llms.txt, llms-full.txt, docs.json, /ai-index.json para Answer Engine Optimization.
  • SEO check automatizado: scripts/check-seo.mjs valida tudo acima no CI após o build.

Lighthouse CI bloqueante valida performance ≥ 0.80, accessibility ≥ 0.90, best-practices ≥ 0.90, SEO ≥ 0.90. Scores atuais: performance 1.0, accessibility 0.95–0.96, best-practices 1.0, SEO 1.0.

Acessibilidade

Positivos: lang=pt-BR, aria-label, aria-hidden, feedback aria-live, navegação por teclado em cards e dropdown da Navbar. Melhorias pendentes: prefers-reduced-motion de forma ampla nos canvas, revisar contraste em textos pequenos.

Performance

Positivos: Astro estático, cache Nginx longo para assets com hash, lazy loading em imagens. Riscos: canvas contínuo (BlackHole/StarBackground), scripts inline extensos, PNGs de hero com ~2 MB.

15. Segurança e infraestrutura ★ novo

Configurações implementadas em 13/05/2026. Documentação detalhada em docs/security.md.

Arquitetura de proteção

Visitante → Cloudflare (proxy + WAF + DDoS) → VPS (UFW + Caddy + Fail2ban)

O IP real da VPS fica oculto atrás do Cloudflare. Tráfego nas portas 80/443 só é aceito de IPs do Cloudflare.

Cloudflare

ConfiguraçãoValor
Nameserversmagdalena.ns.cloudflare.com, michael.ns.cloudflare.com
SSL/TLSFull (strict) — criptografia ponta a ponta com validação de certificado de origem
Always Use HTTPSON
HSTSON — max-age 12 meses, include subdomains
TLS mínimo1.2
Bot Fight ModeON

Hotlink ProtectionON
DDoS L3/L4/L7Ativo — gerenciado automaticamente pelo Cloudflare

Custom rule — Block Bad Paths: bloqueia /.env, /.git, /wp-admin, /xmlrpc.php. Ação: Block.

Rate limiting rule: 100 requests / 10 segundos por IP → Block por 10 segundos (limite do plano Free).

Under Attack Mode: disponível em Security → Overview para ativar CAPTCHA global em caso de ataque severo.

VPS

UFW: portas 80/443 restritas aos IPs do Cloudflare (15 ranges IPv4 + 7 IPv6). SSH (porta 22) aberto. Todo o resto bloqueado.

Fail2ban: proteção SSH — 3 tentativas falhas em 10 min → ban de 48h. Configurado em /etc/fail2ban/jail.local.

Caddy: reverse proxy com SSL automático via Let's Encrypt. Certificados ativos para devsaderiva.com.br, www.devsaderiva.com.br e dashboard.devsaderiva.com.br.
