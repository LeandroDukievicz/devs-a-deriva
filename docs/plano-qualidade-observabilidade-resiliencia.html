Contratos

Aumentar cobertura de testes entre Dashboard e Blog

fase 1
Contrato base das APIs públicas ▾
✓
Inventariar endpoints consumidos pelo blog e congelar o contrato mínimo
Alto Ambos src/lib/posts.ts · src/lib/comments.ts · src/lib/reading-progress-client.ts · dashboard app/api/**
Mapear formato esperado para posts, categorias, autores, comentários, newsletter, progresso de leitura e devs. O resultado deve virar documentação curta e fixtures reutilizáveis.
Solução definitiva sugerida

Implementação: criar uma tabela em docs/dashboard.md ou novo docs/api-contracts.md com endpoint, método, payload aceito, resposta mínima, status de erro e comportamento esperado quando a API falha.

  • Blog: buscar chamadas com rg "PUBLIC_DASHBOARD_URL|/api/" src.
  • Dashboard: buscar rotas públicas com rg "export async function (GET|POST|PATCH)" app/api.
  • Registrar campos obrigatórios e opcionais por endpoint.
  • Adicionar fixtures em tests/fixtures/dashboard-api.ts no blog para respostas válidas, vazias e malformadas.

Critério de pronto: todos os endpoints consumidos pelo blog têm contrato documentado e fixture associada.

Validação: npm run lint no blog e, no dashboard, comando equivalente de check/test se o contrato também for documentado lá.

✓
Adicionar validação defensiva para payload de posts no blog
Alto Blog src/lib/posts.ts · tests/posts.test.ts
O blog precisa continuar previsível quando o dashboard retornar campos ausentes, tipos errados, markdown vazio, categoria desconhecida ou autor incompleto.
Solução definitiva sugerida

Implementação: usar os helpers já existentes em src/lib/posts.ts e ampliar testes para payloads hostis, sem depender de string matching frágil.

  • Testar resposta sem chave de posts, array vazio e item inválido.
  • Testar categoria desconhecida: deve cair em fallback ou descartar com segurança, conforme padrão atual.
  • Testar autor sem foto/social: deve usar fallback documentado.
  • Testar markdown com HTML perigoso e campos opcionais ausentes.

Critério de pronto: falhas de payload externo viram estado vazio, fallback ou erro controlado, nunca crash não tratado.

Validação: npm test -- tests/posts.test.ts e npm run ci:check.

✓
Cobrir contratos de comentários, newsletter e progresso de leitura
Médio Ambos src/components/Comments.astro · src/components/Newsletter.astro · src/lib/reading-progress-client.ts · dashboard app/api/comments/**
Esses fluxos têm escrita pública e dependem de respostas específicas do dashboard. Testar sucesso, erro genérico, rate limit, payload inválido e indisponibilidade.
Solução definitiva sugerida

Implementação: separar o que é teste unitário de contrato e o que é e2e.

  • Blog: testar validadores/clientes puros em tests/comments.test.ts, tests/newsletter-email.test.ts e tests/search.test.ts quando aplicável.

  • Dashboard: adicionar testes dos route handlers públicos para garantir resposta genérica onde houver anti-enumeração.

Critério de pronto: cada fluxo público tem pelo menos um teste para sucesso e um para falha controlada.

Validação: blog npm run ci:check; dashboard npm run check e integração quando rota/banco forem tocados.

Solução definitiva sugerida

Observabilidade

Logs, métricas e sinais operacionais

fase 2
Instrumentação mínima útil ▾
✓
Padronizar logs estruturados nas integrações com o dashboard
Alto Blog src/lib/posts.ts · src/lib/comments.ts · src/pages/rss.xml.ts · src/pages/sitemap.xml.ts
Quando uma chamada ao dashboard falhar, o log precisa ter rota, endpoint, status, duração, tentativa, fallback usado e request id quando existir.
Solução definitiva sugerida

Implementação: criar helper pequeno em src/lib/logger.ts ou src/lib/dashboard-client.ts, mantendo saída em JSON via console.info/warn/error para VPS/Vercel coletarem.

  • Campos mínimos: event, level, route, dashboardEndpoint, status, durationMs, fallback.
  • Nunca logar email, token, conteúdo de comentário, IP bruto ou dados pessoais.
  • Centralizar timeouts e medição de duração no mesmo helper se possível.

Critério de pronto: falhas em posts, RSS, sitemap, comentários/newsletter client-side e progresso de leitura têm sinal rastreável sem vazar dados sensíveis.

Validação: testes unitários do helper e npm run ci:check.

✓
Medir tempo de resposta das rotas SSR críticas
Médio Blog src/pages/index.astro · src/pages/posts/[slug].astro · src/pages/rss.xml.ts · src/pages/sitemap.xml.ts
Rotas SSR precisam indicar quando estão lentas por causa do dashboard, cache ou renderização local.
Solução definitiva sugerida

Implementação: medir duração no começo/fim dos frontmatters ou encapsular chamadas em helper comum.

  • Logar apenas quando passar de um limite inicial, por exemplo 750ms, para evitar ruído.
  • Separar duração total da rota e duração da chamada ao dashboard.
  • Adicionar cabeçalho interno opcional em dev, como x-dda-render-ms, apenas se o adapter permitir sem acoplamento pesado.

Critério de pronto: quando a home/post/RSS/sitemap ficarem lentos, há log suficiente para saber se o gargalo é dashboard, cache ou render.

Validação: npm run build e smoke local das rotas principais.

✓
Expandir healthcheck para sinal de dependências sem transformar em gargalo
Médio Ambos src/pages/health.json.ts · dashboard app/api/health/route.ts
O health atual prova que o app responde. Falta um sinal barato sobre versão, uptime lógico, dashboard configurado e último erro conhecido de integração.
Solução definitiva sugerida

Implementação: manter /health.json rápido e sem chamada remota obrigatória. Expor status, version, timestamp, dashboardConfigured e, se existir cache global, lastDashboardErrorAt.

  • Não fazer healthcheck depender de consulta ao dashboard a cada request.
  • No dashboard, health pode validar DB com timeout curto em rota separada, por exemplo /api/health/deep, se necessário.
  • Documentar diferença entre liveness e readiness.

Critério de pronto: monitor externo consegue distinguir app fora do ar, config ausente e dependência instável.

Validação: npm run build, BASE_URL=... npm run smoke:test em ambiente publicado quando disponível.

✓
Adicionar documentação de eventos observáveis e alertas
Baixo Ambos docs/operations.md · docs/ci-cd.md
Definir quais eventos importam: API offline, falha de newsletter, falha de comentário, rota SSR lenta, cache stale e smoke pós-deploy.
Solução definitiva sugerida

Implementação: criar seção em docs/operations.md com tabela de evento, severidade, onde aparece, ação esperada e dono.

  • Alto: dashboard indisponível por mais de 5 minutos.
  • Médio: newsletter/comentários falhando para usuários.
  • Médio: RSS/sitemap usando cache stale por janela prolongada.
  • Baixo: rota SSR acima do limite ocasionalmente.

Critério de pronto: se um alerta aparecer, existe runbook curto para investigar.

Validação: revisão manual da documentação.

Resiliência

Reduzir dependência frágil do dashboard

fase 3
Cache, fallback e degradação explícita ▾
✓
Implementar stale cache para posts/listagens quando o dashboard oscilar
Crítico Blog src/lib/posts.ts · src/pages/index.astro · src/components/CategoriaPage.astro
O blog deve preferir dados frescos, mas servir o último payload válido por janela controlada quando o dashboard falhar.
Solução definitiva sugerida

Implementação: criar cache em memória por processo para respostas normalizadas de posts, com TTL fresco e janela stale.

  • Fresh TTL inicial: 30s para listagens/posts, alinhado ao comportamento descrito na documentação.
  • Stale window inicial: 6h ou 24h, documentada e logada quando usada.
  • Se não houver cache e o dashboard falhar, mostrar estado offline explícito já previsto pelo projeto.
  • Não cachear respostas inválidas ou malformadas.

Critério de pronto: dashboard fora por curto período não derruba home, categorias e posts já cacheados.

Validação: testes unitários simulando sucesso, falha com cache, falha sem cache e payload inválido; npm run ci:check.

✓
Centralizar cliente HTTP do dashboard com timeout, retry curto e erro tipado
Alto Blog src/lib/dashboard-client.ts (criar) · src/lib/posts.ts · src/lib/comments.ts
Chamadas remotas precisam de comportamento uniforme. Timeout infinito ou retry sem critério aumenta latência e torna falhas difíceis de entender.
Solução definitiva sugerida

Implementação: criar wrapper sobre fetch com AbortController, timeout padrão, retry apenas para GET idempotente e erro normalizado.

  • Timeout inicial: 3s para SSR, 5s para tarefas menos críticas.
  • Retry: no máximo 1 tentativa para GET em erro de rede/5xx, nunca para POST de newsletter/comentário.
  • Erro tipado: DashboardUnavailableError, DashboardInvalidPayloadError, DashboardHttpError.
  • Integrar logs estruturados do item de observabilidade.

Critério de pronto: chamadas ao dashboard têm timeout previsível e falham com erro que o chamador sabe tratar.

Validação: testes do cliente com fetch mockado e npm run ci:check.

✓
Criar fallback específico para RSS, sitemap e AI index
Médio Blog src/pages/rss.xml.ts · src/pages/sitemap.xml.ts · src/pages/ai-index.json.ts
Essas rotas têm valor para crawlers. Quando o dashboard falhar, elas devem servir último dado válido ou uma resposta mínima correta, não HTML de erro.
Solução definitiva sugerida

Implementação: reutilizar cache stale de posts, mas com headers apropriados para crawlers.

  • RSS: último feed válido com comentário XML ou header indicando stale, sem quebrar XML.
  • Sitemap: rotas estáticas sempre presentes; posts entram se cache válido existir.
  • AI index: resposta JSON mínima com categorias e metadados do site se posts estiverem indisponíveis.

Critério de pronto: falha no dashboard não gera resposta inválida para crawlers.

Validação: npm run build, npm run check:seo após build e testes unitários de geração quando possível.

✓
Definir UX de degradação para comentários, newsletter e progresso de leitura
Médio Blog src/components/Comments.astro · src/components/Newsletter.astro · src/lib/reading-progress-client.ts
Interações client-side não devem parecer quebradas quando o dashboard estiver fora. O usuário precisa receber feedback honesto e recuperável.
Solução definitiva sugerida

Implementação: padronizar estados de erro e retry manual nos componentes públicos.

  • Comentários: mostrar estado "temporariamente indisponível" sem esconder comentários já carregados.
  • Newsletter: mensagem genérica, botão reabilitado e sem perder consentimento/email digitado localmente.
  • Progresso: manter localStorage como fonte local e sincronizar depois, sem bloquear leitura.

Critério de pronto: com API interceptada em 500/offline, o usuário entende o estado e não perde ação local desnecessariamente.

Validação: Playwright interceptando dashboard offline para comentários/newsletter/progresso.
